# Устройство orbiter-lan-coop

Что где лежит и какие условия нельзя нарушать — см. [README.md](README.md) этой папки.

> Кода пока нет. Ниже — проект архитектуры, который проверяется прототипом (этапы 0–1 в
> [PLAN.md](PLAN.md)). После прототипа документ переписывается под реальный код.
> Ссылки на ядро Orbiter — в [ORBITER-INTERNALS.md](ORBITER-INTERNALS.md).

## 1. Общая картина

Один и тот же плагин (DLL в `Modules/Plugin`) работает в одной из двух ролей.

```
   Хост                                              Клиент
  ┌──────────────────────────────────┐              ┌──────────────────────────────────┐
  │ Orbiter + OLC (роль host)        │  состояния   │ Orbiter + OLC (роль client)      │
  │                                  ├─────────────►│                                  │
  │ считает физику ВСЕХ кораблей     │  кораблей,   │ навязывает кораблям состояния    │
  │ управляет временем и паузой      │  время       │ хоста, сглаживает между пакетами │
  │ применяет ввод клиентов к        │              │ перехватывает ввод игрока        │
  │ «их» кораблям                    │◄─────────────┤ и отправляет хосту               │
  └──────────────────────────────────┘    ввод      └──────────────────────────────────┘
```

- **Хост** — обычный Orbiter, в котором летает и преподаватель. Его симуляция и есть «правда».
- **Клиент** — обычный Orbiter с тем же сценарием. Его собственная физика кораблей
  подменяется присланными состояниями, ввод игрока уходит на хост.
- **Владение кораблём.** У каждого корабля есть «управляющий»: хост, конкретный клиент или
  никто. Ввод клиента применяется только к кораблю, которым он управляет. Режим «экипаж»
  (двое в одном корабле) — это два участника с правом ввода в один корабль.

## 2. Что происходит при работе

### Подключение

1. Хост запускает сценарий и включает роль host.
2. Клиент получает **тот же мир**. Плагин не может загрузить сценарий во время работы
   (в SDK такой функции нет), поэтому:
   - на этапе 1 оба запускают один и тот же сценарий вручную;
   - с этапа 2 ученик нажимает «Подключиться» в Launchpad, хост передаёт свой текущий
     сценарий, плагин клиента перезапускает Orbiter сразу в него (ключ `-s`) и подключается
     сам (подробнее — [PLAN.md](PLAN.md), этап 2).
   Дополнения по сети не передаются: только проверка и список недостающего.
3. Клиент сверяет набор дополнений и получает соответствие «корабль → управляющий».
   Корабли сопоставляются по имени: handle в ядре — это указатель внутри процесса,
   по сети его не передать. Хост следит, чтобы имена были уникальны.

### Каждый кадр на хосте

1. `clbkPreStep`: применить последний полученный ввод клиентов к их кораблям.
2. Там же снять состояния кораблей (`GetStatusEx`), время, ускорение, паузу и отправить
   клиентам (с частотой 20–30 Гц, а не каждый кадр). Состояние относится к моменту
   `oapiGetSimTime`.
3. Orbiter считает физику.

### Каждый кадр на клиенте

1. Перехватить ввод игрока (`clbkProcessKeyboardImmediate`, `clbkProcessKeyboardBuffered`,
   джойстик через `GetManualControlLevel`) и отправить хосту.
2. `clbkPreStep`: навязать кораблям последние состояния хоста (`DefSetStateEx`), между
   пакетами — сгладить движение. Именно в `clbkPreStep`: в `clbkPostStep` ядро теряет
   навязанную ориентацию (см. [ORBITER-INTERNALS.md](ORBITER-INTERNALS.md), раздел 3).
3. Корабль, который на хосте стоит на поверхности, переводится в статус «стоит» один раз, а
   не каждый кадр.
4. Время: пауза и ускорение берутся с хоста (`oapiSetPause`, `oapiSetTimeAcceleration`).
   Небольшое отставание сим-времени подтягивается, большое — прыжком (`oapiSetSimMJD`).

### Как ввод попадает в корабль на хосте

Подробная таблица клавиш — в [SDK-CHEATSHEET.md](SDK-CHEATSHEET.md), раздел 3.

| Вид ввода | Как применяется на хосте |
|---|---|
| Разовые нажатия (режимы автопилота, RCS, расстыковка, клавиши дополнений) | `VESSEL::SendBufferedKey` — работает на любом корабле, включая клавиши самого дополнения |
| Удерживаемые клавиши RCS, полного газа и тормоза | `IncThrusterGroupLevel_SingleStep` каждый кадр, пока клавиша нажата, — так же, как делает ядро для фокусного корабля |
| Плавный газ, зависание, триммер, тормоза колёс | `Set/IncThrusterGroupLevel`, `SetControlSurfaceLevel`, `SetWheelbrakeLevel` с той же логикой, что в ядре |
| Джойстик | Клиент присылает отклонения по осям; хост переводит их в уровни групп RCS и главного двигателя |
| Собственные удерживаемые клавиши дополнений | Не поддерживаются: SDK не даёт доставить их кораблю вне фокуса |
| Клики в кабине и на панелях | Позже, этап «Экипаж» |

### Каналы связи

| Канал | Протокол | Что передаёт | Частота |
|---|---|---|---|
| Сессия | TCP | подключение, сценарий, проверка дополнений, имена и классы кораблей, владение | при событиях |
| Состояние мира | UDP | положения, скорости, ориентации, вращение, сим-время, ускорение, пауза | 20–30 Гц, на больших ускорениях реже |
| Ввод | UDP | положения органов управления, нажатия клавиш | каждый кадр клиента |

## 3. Почему так

| Решение | Отвергнутые варианты и почему |
|---|---|
| **Авторитетный хост** (вся физика на одном компьютере) | Каждый считает свой корабль (как OMP) — миры расходятся, стыковка игроков и ускорение времени ломаются. Детерминированный lockstep — невозможен: шаг симуляции Orbiter берётся из реальных часов. |
| **Сеть, а не два места за одним ПК** | Ядро знает один фокус, одну камеру, одно окно (`g_focusobj` — около 190 использований). Два комплекта клавиатуры и мыши — переписывание ядра. |
| **Хост — это компьютер с игроком**, без отдельного сервера | Для 2–4 человек по LAN отдельный сервер — лишняя сложность. Позже возможен хост без графики: Orbiter умеет запускаться без графического клиента (консоль «Orbiter Server Console»). |
| **Плагин, а не форк** | Форк надо поддерживать вслед за основным проектом. SDK хватает для прототипа; недостающие хуки — PR в основной проект. |
| **База — `main` на зафиксированном коммите**, цель — ближайший официальный релиз | Релиз 2024 почти на два года старше, в нём нет столкновений кораблей, диалогов на ImGui, `oapiGetKeyState`. |
| **Только LAN** | Интернет требует NAT, защиты и компенсации задержек — не нужно для класса. |

## 4. Что нужно для работы

- Orbiter, собранный из `orbitersim/orbiter` на базовом коммите (см. [README.md](README.md),
  условие 3), одинаковый на всех компьютерах, с одинаковыми дополнениями.
- Windows 10/11 x64. Linux — через Wine/Proton, в роли клиента.
- На клиенте отключены столкновения кораблей (`VesselCollision = FALSE` в `Orbiter.cfg`):
  иначе локальный расчёт столкновений будет спорить с состояниями хоста. Проверяется на этапе 1.

## 5. Главные риски

| Риск | Что известно | Как проверяем |
|---|---|---|
| `DefSetStateEx` 20–30 раз в секунду | Внутри — переинициализация орбиты, пересчёт гравитации, перебор тел и баз, проверка оболочек соседних кораблей. Копящихся побочных эффектов по коду не найдено | Этап 1: плавность и нагрузка |
| Корабль на поверхности | Статус «стоит» задаётся один раз; ядро может само «посадить» неподвижный корабль через 5 с | Этап 1: корабль на полосе не прыгает и не проваливается |
| Сглаживание между пакетами | В ядре уже есть похожий механизм — воспроизведение записи полёта, но он недоступен из SDK | Этап 1; при необходимости — предложить хук в ядро |
| Автостыковка на клиенте | Ядро клиента может само состыковать корабли, оказавшиеся рядом; выключателя в SDK нет | Этап 3 |
| Внутреннее состояние кораблей-дополнений | Скрыто внутри DLL дополнения; новому кораблю его не передать, только через сценарий | Этап 4; сначала только штатные корабли |
| Корабль неизвестного класса | `oapiCreateVesselEx` с отсутствующим классом завершает Orbiter | Клиент проверяет файл класса до создания |
