# Документация orbiter-lan-coop (OLC)

OLC — плагин для космосимулятора Orbiter, который позволяет нескольким людям летать в одной
симуляции с разных компьютеров в локальной сети. Сейчас идёт прототип (этап 3): есть
архитектура, план, карта ядра Orbiter, модель сглаживания, сетевое ядро с тестами и плагин, в
котором пилот подключается кнопкой в Launchpad, получает мир хоста и ведёт свой корабль, а
хост считает физику. Проверка — на стендах.

`orbitersim/orbiter` (у владельца — `~/Documents/github/orbiter`), см. «Условия» ниже.

### Условия, которые нельзя нарушать

1. **Плагин, а не форк.** OLC работает через официальный SDK Orbiter (`Orbitersdk/include`)
   и не требует изменённого ядра. Если без хука в ядре не обойтись — это отдельное решение,
   которое оформляется PR в `orbitersim/orbiter`, а не правкой у себя.
2. **Клон Orbiter только для чтения.** В нём ничего не меняем и не собираем «под себя».
   Единственное разрешённое действие — обновление из GitHub (`git pull --ff-only`) при
   сверке с upstream. Карта ядра и все выводы о нём живут здесь, в `docs/ru/ORBITER-INTERNALS.md`.
3. **Базовый коммит Orbiter — последний сверенный коммит `main`:** сейчас `a7a3396e`
   (2026-11-12). Все ссылки на код ядра в документации указаны для него. Базовый коммит
   переносится вперёд после каждой сверки с upstream (раздел «Сверка с Orbiter» в
   `docs/ru/ORBITER-INTERNALS.md`), чтобы OLC не застрял между релизами.
4. **Физику считает только хост.** Клиент не принимает решений о движении кораблей: он
   показывает присланное состояние и отправляет ввод. Никакой «своей физики» у клиента.
5. **Только LAN.** Протокол не рассчитан на интернет и не защищён (см. `SECURITY.md`).

### Правила работы над проектом

- **Языки (решение 29).** Документация — на русском и английском, обе версии полные.
  Источник — русская (`README.ru.md`, `CHANGELOG.ru.md`, `docs/ru/`), английская
  (`README.md`, `CHANGELOG.md`, `docs/`) — её полный перевод. Любая правка документа — сразу
  в обеих версиях, в одном коммите; структуру пар (заголовки, таблицы, блоки кода)
  проверяет `tools/doccheck` в CI. Термины Orbiter и SDK не переводятся.
- Комментарии в коде, скриптах и примерах настроек — только на английском. Всё, что
  плагин пишет в лог Orbiter, в окна и в сообщения об ошибках, — тоже на английском.
- Код должен работать и быть хорошим: простым, понятным и удобным для доработки людьми и
  ИИ-агентами. Понятность важнее изящества, сложность — только когда она нужна.
- После любого изменения сверьте с кодом `README.md`, `docs/` и комментарии. Они должны
  описывать текущее состояние, а не прошлое.
- Не оставляйте неиспользуемых функций, файлов и зависимостей.
- На стендах (Windows, Linux) ИИ-агент по SSH собирает, запускает и останавливает Orbiter и
  OLC и читает логи. Установку программ, системные настройки, снапшоты и docker делает
  только владелец (решение 20, схема — `STANDS.md`). Агент работает только с машинами из
  `stands.yaml`; если файла нет — стендов нет (решение 26). Исключение — машины с
  `access: full`: их владелец отдал агенту целиком, и там он сам ставит пакеты и
  перезагружает (решение 27).
- Git: до первого зафиксированного релиза (около 0.1) агент сам коммитит законченные
  задачи и отправляет их прямо в `main` — с разрешения владельца, только в этом проекте.
  После релиза — работа в ветках. Сообщения коммитов — на английском (решение 38).
- Каталог проверочной сборки всегда один и тот же — `orbiter-lan-coop.out` — и он
  перечислен в `.gitignore`.

### Автономная работа

Владелец днём занят, поэтому ИИ-агент работает над проектом сам по пакету задач, который
владелец одобрил. Правила:

1. **Только одобренное.** Агент делает пункты `PLAN.md` и задачи, о которых договорились в
   чате. Исследования кода и карту ядра агент добавляет в очередь и выполняет сам
   (решение 21); всё остальное новое — через вопрос.
2. **Развилка — вопрос, а не догадка.** Вопрос с вариантами и рекомендацией записывается в
   `QUESTIONS.md`, агент докладывает о нём в основную сессию владельца (решение 42), сам
   переключается на другую независимую задачу. Принятое решение записывается в `DECISIONS.md`.
3. **Нужна Windows или Linux — ждём стенд.** Обходных путей не ищем.
4. **Модели** (решение 48). Основная сессия владельца работает на Opus: архитектура,
   постановка задач, проверка результата и задачи со статусом «(основная сессия)» — их она
   делает сама. Запуск по расписанию работает на Sonnet: реализация и разбор кода по
   готовому заданию. Haiku — поиск по коду. Субагент Opus — только когда нужна вторая
   параллельная работа уровня Opus. Результат субагента всегда проверяет тот, кто его
   вызвал. Какой задаче какая модель, решает основная сессия как тимлид: простую задачу
   отдаёт Sonnet, сложную помечает «(основная сессия)» и делает сама (решение 49).
5. **Расписание (время UTC+5).**
   - Запуск по расписанию — каждый час в :00 (решение 45). Он дёшево проверяет
     блокировку, лимиты и очередь и, если работы нет, сразу засыпает; если есть —
     работает подряд, пока есть работа и лимит. Оборвавшийся запуск подхватит
     следующий.
   - Блокировка `orbiter-lan-coop.out/.agent-lock` одна на всех: строка «время кто»
     (`scheduled` или `main`). Её ставит и основная сессия, когда правит файлы проекта.
     Работающий обновляет время перед каждым шагом; блокировка старше 40 минут считается
     брошенной.
   - Взятая задача сразу получает статус «в работе» отдельным коммитом. Остановка посреди
     задачи — отметка «остановился: …» в её строке `PLAN.md`, тоже в коммите. Так
     следующий запуск продолжает задачу, а не берёт уже сделанную.
   - Других ограничений по времени суток и дням недели нет: работу ограничивают только
     лимиты окна и недели (решение 41).
6. **Лимиты** (решения 22, 40, 41 и 45). Перед каждым куском работы агент смотрит расход:
   - 5-часовое окно: новую работу — только ниже 90%; начатый шаг доводится до целого
     состояния, но не выше 95%: владелец всегда может написать сообщение;
   - неделя тратится к сбросу (суббота, 18:00): в каждый момент израсходовано не больше
     (доля прошедшей недели) × 100% + 5%. Кончиться за несколько часов до сброса можно,
     за сутки — нет;
   - лимит не тратится ради расхода: если полезной работы нет (всё ждёт стендов или
     ответа владельца), агент заканчивает;
   - если порог пройден посреди работы, агент доводит шаг до целого состояния и
     записывает, где остановился; через час проверка повторится сама.
7. **Сверка с Orbiter.** Если в журнале сверок (`ORBITER-INTERNALS.md`, раздел 13) нет
   записи за сегодня, первым делом — сверка с upstream по описанному там порядку.
8. **Без лишних остановок** (решение 37). Агент работает по очереди подряд и не ждёт
   владельца после каждого пакета. Ждёт только в двух случаях: упёрся в лимит или нужно
   решение владельца (обход дорогой, можно что-то сломать, выбор пути). Работа ради работы
   не делается.
9. **Отчёт.** Каждый пакет заканчивается отчётом: что сделано, что проверено, что нет,
   сколько лимита ушло. Запуск по расписанию, который поработал, отправляет отчёт в
   основную сессию владельца, а она решает, когда известить владельца (решение 42);
   пустые проверки не докладываются.
10. **Git.** Законченную задачу агент коммитит и отправляет в `main` (см. «Правила работы
   над проектом»); незаконченное в коммит не идёт.
