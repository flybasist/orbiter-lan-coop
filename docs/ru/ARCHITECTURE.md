# Устройство orbiter-lan-coop

Что где лежит и какие условия нельзя нарушать — см. [README.md](README.md) этой папки.

> Ниже — архитектура прототипа ([PLAN.md](PLAN.md)). Код этапа 3 есть (раздел 6): хост рассылает
> состояние мира, клиент его показывает и управляет своим кораблём, стыковки повторяются у всех.
> Где написано «планируется», этого в коде ещё нет.
> Ссылки на ядро Orbiter — в [ORBITER-INTERNALS.md](ORBITER-INTERNALS.md).

## 1. Общая картина

Один и тот же плагин (DLL в `Modules/Plugin`) работает в одной из двух ролей.

```
   Хост                                              Клиент
  ┌──────────────────────────────────┐              ┌──────────────────────────────────┐
  │ Orbiter + OLC (роль host)        │  состояния   │ Orbiter + OLC (роль client)      │
  │                                  ├─────────────►│                                  │
  │ считает физику ВСЕХ кораблей     │  кораблей,   │ навязывает кораблям состояния    │
  │ управляет временем и паузой      │  время       │ хоста, сглаживает между пакетами │
  │ применяет ввод клиентов к        │              │ перехватывает ввод игрока        │
  │ «их» кораблям                    │◄─────────────┤ и отправляет хосту               │
  └──────────────────────────────────┘    ввод      └──────────────────────────────────┘
```

- **Хост** — обычный Orbiter, в котором летает и руководитель полётов. Его симуляция и есть «правда».
- **Клиент** — обычный Orbiter с тем же сценарием. Его собственная физика кораблей
  подменяется присланными состояниями, ввод игрока уходит на хост.
- **Владение кораблём.** У каждого корабля есть «управляющий»: хост, конкретный клиент или
  никто. Ввод клиента применяется только к кораблю, которым он управляет. Режим «экипаж»
  (двое в одном корабле) — это два участника с правом ввода в один корабль.

## 2. Что происходит при работе

### Подключение

1. Хост запускает сценарий и включает роль host.
2. Клиент получает **тот же мир**. Функции SDK для загрузки сценария во время работы нет,
   поэтому:
   - на этапе 1 оба запускают один и тот же сценарий вручную;
   - с этапа 2 пилот нажимает «Подключиться» в Launchpad, хост передаёт свой текущий
     сценарий, плагин клиента сам выбирает его в Launchpad и запускает в том же процессе
     ([ORBITER-INTERNALS.md](ORBITER-INTERNALS.md), раздел 18; запасной путь — перезапуск
     Orbiter с ключом `-s`) и подключается сам (подробнее — [PLAN.md](PLAN.md), этап 2).
   Дополнения по сети не передаются: только проверка и список недостающего.
3. Клиент сверяет набор дополнений и получает соответствие «корабль → управляющий».
   Корабли сопоставляются по имени: handle в ядре — это указатель внутри процесса,
   по сети его не передать. Хост следит, чтобы имена были уникальны.

### Каждый кадр на хосте

1. `clbkPreStep`: применить последний полученный ввод клиентов к их кораблям.
2. Там же снять состояния кораблей (`GetStatusEx`), время, ускорение, паузу и отправить
   клиентам (до 60 раз в секунду, по умолчанию 60, а не каждый кадр). Состояние относится к моменту
   `oapiGetSimTime`.
3. Orbiter считает физику.

### Каждый кадр на клиенте

1. Перехватить ввод игрока (`clbkProcessKeyboardImmediate`, `clbkProcessKeyboardBuffered`,
   джойстик через `GetManualControlLevel`) и отправить хосту.
2. `clbkPreStep`: навязать кораблям последние состояния хоста (`DefSetStateEx`), между
   пакетами — сгладить движение. Именно в `clbkPreStep`: в `clbkPostStep` ядро теряет
   навязанную ориентацию (см. [ORBITER-INTERNALS.md](ORBITER-INTERNALS.md), раздел 3).
3. Корабль, который на хосте стоит на поверхности, переводится в статус «стоит» один раз, а
   не каждый кадр.
4. Время: пауза и ускорение берутся с хоста (`oapiSetPause`, `oapiSetTimeAcceleration`).
   Если сим-время клиента разошлось с хостом больше порога (`TimeSyncThreshold`, по умолчанию
   0,1 с, на ускорении — × ускорение), оно переставляется прыжком (`oapiSetSimMJD`); меньшее
   расхождение только учитывается в журнале.

### Пауза и неактивное окно

На паузе Orbiter не вызывает `clbkPreStep`, а клавиатурные колбэки получает только активное
окно. Поэтому у плагина есть своё скрытое окно Windows с таймером: его сообщения приходят
всегда. По таймеру плагин на паузе принимает пакеты и, получив от хоста снятие паузы,
вызывает `oapiSetPause(false)`. Флаг паузы есть в каждом пакете `WORLD_STATE`.
Отдельного сетевого потока нет (решение 23): сокеты неблокирующие, приём и отправка идут
в главном потоке Orbiter — в `clbkPreStep`, а на паузе по таймеру скрытого окна.
Подробности — [ORBITER-INTERNALS.md](ORBITER-INTERNALS.md), раздел 14.

### Интерфейс

- **Launchpad**, вкладка «Extra», пункт «OLC - LAN co-op»: диалог Win32 с ролью (хост или
  клиент), адресом хоста, портом, именем игрока и кнопкой «Connect». Настройки диалог сохраняет
  в `Config\OrbiterLanCoop.cfg` (`saveConfig`).
- **В симуляции** — сообщения пилоту текстом на экране (`oapiCreateAnnotation`, 20 с): какой
  корабль его, «только просмотр» на чужом, отказы. Состояние подключения и статистика сети —
  в `Orbiter.log`. У руководителя полётов слева постоянная надпись-сводка: игроки, их корабли и задержка до хоста (`core/player_summary.h`, из `PLAYERS`).
- Без графического клиента (хост в консольном режиме) окон нет — только лог.

Подробности и подвохи — [ORBITER-INTERNALS.md](ORBITER-INTERNALS.md), раздел 16.

### Как ввод попадает в корабль на хосте

Подробная таблица клавиш — в [SDK-CHEATSHEET.md](SDK-CHEATSHEET.md), раздел 3.

| Вид ввода | Как применяется на хосте |
|---|---|
| Разовые нажатия (режимы автопилота, RCS, расстыковка, клавиши дополнений) | `VESSEL::SendBufferedKey` — работает на любом корабле, включая клавиши самого дополнения |
| Удерживаемые клавиши RCS, полного газа и тормоза | `IncThrusterGroupLevel_SingleStep` каждый кадр, пока клавиша нажата, — так же, как делает ядро для фокусного корабля |
| Плавный газ, зависание, триммер, тормоза колёс | `Set/IncThrusterGroupLevel`, `SetControlSurfaceLevel`, `SetWheelbrakeLevel` с той же логикой, что в ядре |
| Джойстик | Клиент присылает отклонения по осям; хост переводит их в уровни групп RCS и главного двигателя |
| Собственные удерживаемые клавиши дополнений | Не поддерживаются: SDK не даёт доставить их кораблю вне фокуса |
| Клики в кабине и на панелях | Позже, этап «Экипаж» |

### Каналы связи

| Канал | Протокол | Что передаёт | Частота |
|---|---|---|---|
| Сессия | TCP | подключение, сценарий, проверка дополнений, имена и классы кораблей, владение | при событиях |
| Состояние мира | UDP | положения, скорости, ориентации, вращение, сим-время, ускорение, пауза | 60 Гц по умолчанию (решение 36), на паузе — 5 Гц |
| Ввод | UDP | положения органов управления, нажатия клавиш | каждый кадр клиента |

## 3. Почему так

| Решение | Отвергнутые варианты и почему |
|---|---|
| **Авторитетный хост** (вся физика на одном компьютере) | Каждый считает свой корабль (как OMP) — миры расходятся, стыковка игроков и ускорение времени ломаются. Детерминированный lockstep — невозможен: шаг симуляции Orbiter берётся из реальных часов. |
| **Сеть, а не два места за одним ПК** | Ядро знает один фокус, одну камеру, одно окно (`g_focusobj` — около 190 использований). Два комплекта клавиатуры и мыши — переписывание ядра. |
| **Хост — это компьютер с игроком**, без отдельного сервера | Для 2–4 человек по LAN отдельный сервер — лишняя сложность. Позже возможен хост без графики: Orbiter умеет запускаться без графического клиента (консоль «Orbiter Server Console»). |
| **Плагин, а не форк** | Форк надо поддерживать вслед за основным проектом. SDK хватает для прототипа; недостающие хуки — PR в основной проект. |
| **База — `main` на зафиксированном коммите**, цель — ближайший официальный релиз | Релиз 2024 почти на два года старше, в нём нет столкновений кораблей, диалогов на ImGui, `oapiGetKeyState`. |
| **Только LAN** | Интернет требует NAT, защиты и компенсации задержек — не нужно для класса. |

## 4. Что нужно для работы

- Orbiter, собранный из `orbitersim/orbiter` на базовом коммите (см. [README.md](README.md),
  условие 3), одинаковый на всех компьютерах, с одинаковыми дополнениями.
- Windows 10/11 x64. Linux — через Wine/Proton, в роли клиента.
- На клиенте отключены столкновения кораблей (`VesselCollision = FALSE` в `Orbiter.cfg`):
  иначе локальный расчёт столкновений будет спорить с состояниями хоста. Проверяется на этапе 1.

## 5. Главные риски

| Риск | Что известно | Как проверяем |
|---|---|---|
| `DefSetStateEx` каждый кадр клиента (около 60 раз в секунду) | Внутри — переинициализация орбиты, пересчёт гравитации, перебор тел и баз, проверка оболочек соседних кораблей. Копящихся побочных эффектов по коду не найдено | Этап 1: плавность и нагрузка |
| Корабль на поверхности | Статус «стоит» задаётся один раз; ядро может само «посадить» неподвижный корабль через 5 с | Этап 1: корабль на полосе не прыгает и не проваливается |
| Сглаживание между пакетами | В ядре уже есть похожий механизм — воспроизведение записи полёта, но он недоступен из SDK. Модель сглаживания: свой буфер с интерполяцией Эрмита справляется ([SMOOTHING.md](SMOOTHING.md)) | Этап 1; при необходимости — предложить хук в ядро |
| Автостыковка на клиенте | Ядро клиента может само состыковать корабли, оказавшиеся рядом; выключателя в SDK нет | Этап 3 |
| Внутреннее состояние кораблей-дополнений | Скрыто внутри DLL дополнения; новому кораблю его не передать, только через сценарий | Этап 4; сначала только штатные корабли |
| Корабль неизвестного класса | `oapiCreateVesselEx` с отсутствующим классом завершает Orbiter | Клиент проверяет файл класса до создания |

## 6. Код

Код делится на две части:

| Часть | Где | Что в ней |
|---|---|---|
| Сетевое ядро `olc-core` | `core/` | Протокол, сериализация, буфер интерполяции, таблица кораблей, сокеты. Не зависит от Orbiter и его SDK, поэтому собирается и тестируется на любой системе, включая Mac |
| Плагин `OrbiterLanCoop` | `plugin/` | Тонкая прослойка между SDK Orbiter и `olc-core`: снимает и навязывает состояния. Собирается только под Windows, против SDK собранного Orbiter (`QUICKSTART.md`, раздел 5) |

Так большая часть логики проверяется тестами без запуска Orbiter, а в плагине остаётся
только то, что нельзя проверить без симулятора.

Тесты лежат в `tests/`, по одному исполняемому файлу на часть ядра, и запускаются через
CTest. Сторонних библиотек для тестов нет: проверки — макрос `CHECK` из `tests/check.h`.

```bash
cmake -S . -B orbiter-lan-coop.out
cmake --build orbiter-lan-coop.out
ctest --test-dir orbiter-lan-coop.out
```

Сейчас в `olc-core`:

| Файл | Что в нём |
|---|---|
| `core/messages.h` | Номера типов сообщений и упаковка с разбором тел всех сообщений TCP и UDP (`PROTOCOL.md`, разделы 5 и 6); заголовки к ним — `header.h`. Разбор отвергает обрезанное тело и лишние байты в конце |
| `core/protocol.h` | Постоянные протокола: версия, порт, сигнатура UDP, предельные размеры; сравнение порядковых номеров UDP-пакетов с учётом переполнения счётчика; время следующей отправки периодического пакета (`nextSendTime`: от запланированного времени, чтобы при 60 кадрах в секунду `INPUT` и `WORLD_STATE` уходили каждый кадр, а не через кадр) |
| `core/header.h` | UDP-заголовок (запись и проверка: размер, сигнатура, версия) и TCP-кадры: `makeTcpFrame` собирает сообщение с длиной, `TcpFrameReader` достаёт целые сообщения из потока и закрывает разбор при недопустимой длине |
| `core/interpolation.h` | `InterpolationBuffer` — буфер интерполяции одного корабля на клиенте (`SMOOTHING.md`): принимает состояния из `WORLD_STATE` по сим-времени хоста, отбрасывает опоздавшие и выдаёт состояние на любой момент: положение — Эрмит, скорости — линейно, ориентация — slerp. Между летящим и стоящим пакетами и при смене опорного тела не интерполирует; когда буфер кончился, продолжает движение по последней скорости. Какой момент показывать (задержка показа `DisplayDelay`, по умолчанию 30 мс, × ускорение), решает вызывающий |
| `core/scenario_filter.h` | Подготовка присланного сценария: убирает корабли классов, которых нет у клиента (иначе Orbiter аварийно завершится при загрузке), и переводит на оставшийся корабль фокус и камеру |
| `core/session_table.h` | `SessionTable` — таблица одной сессии. На хосте: приём клиентов с пределом игроков (хост тоже игрок; по умолчанию 4, от 2 до 8 — решение 14), выдача `net_id` по порядку без повторного использования, владение кораблями и проверка, чей ввод применять; взять и отпустить корабль (один клиент — один корабль), ушедший клиент оставляет корабль без владельца и закрывает его для других на 60 с. На клиенте: та же таблица по `VESSELS`, `VESSEL_ADDED`, `VESSEL_REMOVED` и `OWNERSHIP` |
| `core/socket.h` | Обёртка над сокетами: `UdpSocket`, `TcpConnection` (неблокирующее подключение, очередь отправки с досылкой частичных записей, приём в `TcpFrameReader`), `TcpListener`; адреса только IPv4 цифрами (`parseIpv4`). Все сокеты неблокирующие и ничего не ждут, потоков внутри нет: сеть работает в главном потоке Orbiter (решение 23). Winsock и POSIX — в одном `socket.cpp`; сеть запускается `startNetwork` из `clbkSimulationStart`, не из `InitModule`. Windows-часть проверена на стенде (этап 0) |
| `core/attitude.h` | Перевод углов Эйлера `arot` в кватернион и обратно по той же формуле, что в ядре Orbiter (`Vessel.cpp:914`), и slerp между кватернионами |
| `core/host_link.h` | `HostLink` — сеть хоста: слушает TCP и UDP, ведёт рукопожатие (`HELLO` → `WELCOME`/`REJECT` → `BODIES`, `VESSELS`, `OWNERSHIP`, затем `CLASSES_MISSING` и `UDP_READY`), отвечает `PONG`, принимает `INPUT` от владельца корабля (последний по кораблю, `latestInput`), обрабатывает `OWNER_REQUEST` (взять, отпустить; отказ — `OWNER_DENIED`, изменения — `OWNERSHIP` всем), рассылает `WORLD_STATE` и `FUEL` с делением на пакеты до 1200 байт, `LANDED`, `VESSEL_ADDED` и `VESSEL_REMOVED` по TCP, `DOCK` (`sendDock`; текущие связки — и тем, кто подключился позже), `ANIM_STATE` (`sendAnimState`) и `NAV_STATE` (`sendNavState`; последние значения — тоже подключившимся позже); принимает `NAV_STATE` только от владельца корабля (`takeNavStates`) и рассылает остальным; принимает `KEY` своего корабля (`takeKeys`); принимает `TIME_REQUEST` только от руководителя полётов (`HostConfig::director`, `takeTimeRequests`) и рассылает `PLAYERS` (при входе, выходе, смене владения и раз в 2 с); наблюдатель корабль взять не может; на `HELLO` без номера сценария отвечает `SCENARIO` (файл даёт плагин через `makeScenario`) и закрывает соединение; ушедших клиентов (в том числе молчащих `kSilenceTimeout` = 15 с) убирает из `SessionTable`. Orbiter не знает: корабли и состояния даёт плагин |
| `core/client_link.h` | `ClientLink` — сеть клиента: подключение и рукопожатие, таблица кораблей и тел хоста, приём `WORLD_STATE` (проверка сессии и порядка) в буферы интерполяции по кораблям, `FUEL`, `LANDED`, новые и удалённые корабли (`takeVesselChanges`), запросы взять и отпустить корабль (`requestTake`, `requestRelease`) и отказы (`takeOwnerDenials`), разовые нажатия `KEY` (`sendKey`), запросы паузы и ускорения от руководителя `TIME_REQUEST` (`sendTimeRequest`), список игроков `PLAYERS` (`players`), стыковки `DOCK` (`takeDocks`), приём `SCENARIO` по запросу, `INPUT` не чаще 60 раз в секунду (`sendInput`), `PING` раз в секунду и задержка туда-обратно, закрытие, если хост молчит 15 с. Плагин спрашивает состояние корабля на момент показа (`sampleVessel`), для замеров — последнее полученное (`latestVessel`) |
| `core/player_summary.h` | Текст сводки игроков для экрана руководителя полётов: игроки, роли, корабли, задержка (из `PLAYERS`); без вызовов Orbiter, покрыт тестом |
| `core/keymap.h` | Раскладка клавиш: читает `keymap.cfg` Orbiter, превращает удерживаемые клавиши управления кораблём в биты `INPUT.keys` и гасит их в состоянии клавиатуры, чтобы Orbiter не вёл локальную копию. Вращение и перемещение RCS делят клавиши, поэтому уходят оба бита, а хост выбирает по режиму RCS корабля |
| `core/client_clock.h` | `ClientClock` — часы показа на клиенте: какой момент сим-времени хоста показывать (на задержку показа позади хоста). Между пакетами идут сами со скоростью ускорения хоста, малую ошибку исправляют плавно, большую — прыжком |
| `core/serialize.h` | `Writer` и `Reader`: запись и чтение полей `u8`…`f64` и `str` little-endian, а также байтов как есть (файл сценария). `Reader` никогда не читает за концом данных: при нехватке байтов чтение возвращает `false`, и все следующие чтения тоже |

| `plugin/OrbiterLanCoop.cpp` | Модуль Orbiter: роль из настроек, колбэки сессии и кадра, скрытое окно с таймером для работы на паузе (решение 23) |
| `plugin/config.h` | Настройки из `Config\OrbiterLanCoop.cfg` (пример — `plugin/OrbiterLanCoop.cfg`): роль, адрес хоста, порт, частота, задержка показа, трасса; запись файла из Launchpad (`saveConfig`) |
| `plugin/host_side.h` | Роль «хост»: снимает состояния кораблей (`GetStatusEx`) в `clbkPreStep`, рассылает `WORLD_STATE` с частотой `StateRate`, `FUEL` раз в секунду, `LANDED` при посадке и повтором для стоящих; корабли, созданные и удалённые во время сессии, — `VESSEL_ADDED` и `VESSEL_REMOVED`; хост-игрок владеет кораблём в своём фокусе, сервер без графики — никаким; каждый кадр вне паузы применяет `INPUT` пилотов (`vessel_control.h`), `INPUT` старше 0,5 с не применяется; при смене набора клавиш пилота пишет в журнал, что они сделали (режим и уровни RCS, двигатели, триммер, тормоза, вращение) |
| `plugin/client_side.h` | Роль «клиент»: пауза и ускорение как у хоста, сим-время рядом с моментом показа (прыжок при расхождении больше `TimeSyncThreshold`), топливо, посадка один раз, состояния кораблей через `DefSetStateEx` в `clbkPreStep`, уровни двигателей; список кораблей как у хоста: недостающие создаёт, если класс установлен, лишние и удалённые хостом удаляет (кроме последнего корабля); свой корабль — фокусом на свободный, Ctrl+Alt+U отпускает, уведомления на экране и в журнале; шлёт `INPUT` для своего корабля каждый кадр (клавиши — пока он в фокусе, плюс джойстик) и гасит клавиши управления локально |
| `plugin/vessel_control.h` | Применение `INPUT` пилота к кораблю на хосте так, как ядро Orbiter делает для корабля в фокусе: RCS одним шагом по режиму RCS, полные главный и тормозной двигатели, kill rot, газ и зависание 0,2 в секунду, триммер 0,25 в секунду, тормоза колёс |
| `plugin/launchpad_item.h` | Пункт «OLC - LAN co-op» в Launchpad (вкладка «Extra»): роль, адрес, порт, имя; кнопка «Connect» получает сценарий хоста (`HELLO` без номера) и запускает его |
| `plugin/scenario_launch.h` | Запуск присланного сценария: корабли без установленного класса убираются (`scenario_filter.h`), запись в `Scenarios\OLC\Host world.scn`, выделение в списке Launchpad и нажатие «Launch» (`ORBITER-INTERNALS.md`, раздел 18) |
| `plugin/trace.h` | Запись положения одного корабля в CSV у хоста и клиента — для замера расхождения |
| `plugin/wall_clock.h` | Часы стены для замеров задержки: `oapiGetSysTime` не видит кадров длиннее 0,1 с (`ORBITER-INTERNALS.md`, раздел 4) |
