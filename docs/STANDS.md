# Стенды

Как проверять OLC на реальных машинах и как ИИ-агент с ними работает. Документ общий: у
каждого участника или форка свой набор машин. Здесь — какие системы имеет смысл брать,
какие роли бывают у машин и как их подготовить.

Свои машины каждый описывает в файле `stands.yaml` в корне репозитория (пример —
[`stands.example.yaml`](../stands.example.yaml)). Файл в `.gitignore` и в git не попадает.

> Гипотезы из раздела 7 ещё не проверены: они проверяются на этапе 0 ([PLAN.md](PLAN.md)).

## 1. Схема: один мозг, много рук

- **Мозг** — сессия ИИ-агента на машине разработчика. У неё весь контекст: `docs/`,
  решения, очередь задач. Отдельный агент на каждом стенде не ставится: у него был бы свой
  контекст, синхронизация через git и тот же лимит аккаунта.
- **Руки** — SSH на стенды. Сборка, запуск и остановка Orbiter и OLC, сбор логов,
  копирование собранных файлов. Работу на стенде можно поручить субагенту: он пользуется
  тем же SSH.
- **Глаза** — только там, где без экрана не обойтись (раздел 6).

## 2. Поддерживаемые системы

Orbiter — программа для Windows x64. Всё остальное запускает её через эмуляцию или Wine.

| Система | Что на ней можно | Смысл как стенд |
|---|---|---|
| Windows 10/11 x64 | Всё: сборка, хост, клиент, хост без графики | Эталон. Нужна хотя бы одна |
| Windows 11 ARM (виртуальная машина на Mac) | Всё, но Orbiter x64 идёт через эмуляцию | Удобно для разработки; FPS и плавность не показатель |
| Linux x64 + Wine или Proton (в том числе Steam Deck) | Клиент и хост; сборка плагина — нет | Проверка клиентов под Linux |
| Linux x64 или ARM без Wine | Сборка и тесты сетевого ядра `olc-core` | Вторая машина для сетевых тестов; Orbiter не запускается |
| macOS | Сборка и тесты `olc-core`, сессия агента | Orbiter нативно не запускается; Wine на Mac проект не проверяет |
| FreeBSD, другие системы, 32-битная Windows | — | Не поддерживаются ни Orbiter, ни OLC. Не имеет смысла |

Для Linux рекомендуем Debian 13 или Ubuntu LTS: для них WineHQ выпускает свои пакеты.

## 3. Роли машин

Значения поля `roles` в `stands.yaml`:

| Роль | Что делает машина | Что нужно |
|---|---|---|
| `build` | Собирает Orbiter и OLC | Windows, Visual Studio (раздел 8.1) |
| `client` | Запускает Orbiter с картинкой и подключается к хосту | Видеокарта с DirectX 9 (или Vulkan под Wine) |
| `host` | Запускает Orbiter с картинкой и ведёт сессию | То же, что `client` |
| `headless-host` | Ведёт сессию без графического клиента («Orbiter Server Console») | Видеокарта не нужна |
| `core-tests` | Собирает и тестирует `olc-core`, участвует в сетевых тестах | Компилятор C++ и CMake |

## 4. Сколько машин нужно

- **Минимум для начала (этап 0 и начало этапа 1):** одна Windows-машина с ролями `build`,
  `host` и `client`. Хост и клиент — два экземпляра Orbiter на ней
  ([ORBITER-INTERNALS.md](ORBITER-INTERNALS.md), раздел 15).
- **Для этапа 1 целиком:** вторая машина в той же сети — чтобы проверить настоящие потери и
  задержки, а не обмен внутри одной машины. Хотя бы одна из двух — Windows x64 без
  эмуляции: на ней оценивается плавность.
- **Дальше по желанию:** Linux через Wine или Proton, Steam Deck, разные версии Windows —
  проверка клиентов, а не идеи.

## 5. Доступ

1. На каждой машине — отдельный пользователь (рекомендуем `olc`), вход по SSH только по ключу.
2. Отдельный ключ для стендов на машине разработчика (например, `~/.ssh/olc_stands`) и
   короткие имена машин в `~/.ssh/config`. Адрес, пользователь и ключ живут только там.
3. Имя из `~/.ssh/config` вписывается в поле `ssh` в `stands.yaml` — по нему работает агент.
4. Windows: компонент OpenSSH Server, команды — через PowerShell.
5. Доступ только к самим машинам — не к гипервизору и не к его API.

## 6. Что делает агент, а что владелец стенда

| Действие | Кто |
|---|---|
| Установка программ (Visual Studio, DirectX SDK, CMake, Wine), системные настройки, брандмауэр | Владелец |
| Снапшоты машин и откат | Владелец |
| Команды docker | Владелец |
| Сборка Orbiter и OLC, запуск и остановка Orbiter, копирование файлов OLC, чтение логов | Агент (решение 20 в [DECISIONS.md](DECISIONS.md)) |

Так работает машина с `access: limited` в `stands.yaml` — например, личная машина, данная
на время. Если машина целиком отдана агенту (`access: full`), он сам ставит и удаляет пакеты,
перезагружает её и меняет настройки (решение 27). Пароли агент не вводит: для установки
пакетов на такой машине нужен `sudo` без пароля.

### Как смотреть на картинку

Orbiter — оконное приложение. В Windows программа, запущенная по SSH, работает в
невидимой служебной сессии, а не на рабочем столе. Поэтому:

- **Главное — обходиться без экрана.** Плагин пишет в лог задержку, потери и расхождение
  положений; агент читает лог по SSH. Экран нужен только для итоговой проверки плавности.
- **Виртуальная машина на Mac** (`screen: mac-window`): её окно — окно на экране Mac;
  агент смотрит и кликает в нём через управление компьютером (computer use).
- **Серверный гипервизор** (`screen: console`): консоль в браузере, в гипервизор входит владелец.
- **Без графического клиента Orbiter работает прямо по SSH** (проверено): открывается
  «Orbiter Server Console», симуляция идёт, плагин загружается. Для сетевых тестов без
  картинки задача планировщика не нужна.
- **Запуск Orbiter на видимом рабочем столе Windows из SSH:** автовход пользователя и задача
  планировщика «OLC Run Orbiter», которая запускается только по команде и выполняет
  [`tools/stands/run-orbiter.ps1`](../tools/stands/run-orbiter.ps1) в сессии пользователя.
  Задание (какие копии Orbiter с какими ключами запустить, когда снять экран) агент кладёт в
  `C:\olc\run-orbiter.json`; результат — журнал и снимки в `C:\olc\run-orbiter`. Задача
  создаётся один раз скриптом [`tools/stands/register-run-task.ps1`](../tools/stands/register-run-task.ps1)
  с согласия владельца машины.
- **Linux:** запуск в графической сессии пользователя (переменная `DISPLAY`).

## 7. Особенности виртуализации (гипотезы, проверяются на этапе 0)

- **Виртуальная машина без проброса видеокарты** (типично для Proxmox и других серверных
  гипервизоров). Нормального 3D нет: D3D9Client в Windows, скорее всего, не запустится или
  будет очень медленным; Wine с DXVK требует Vulkan. Такая машина — для хоста без графики,
  сборок и сетевых тестов. С проброшенной видеокартой (PCI passthrough) она становится
  полноценным клиентом.
- **Windows 11 ARM.** Orbiter x64 работает через встроенную в Windows эмуляцию x64:
  годится для разработки и проверки функций, не для замеров FPS.
- **Linux ARM.** Orbiter не запустить (Wine требует эмуляции x86), но сетевое ядро OLC от
  Orbiter не зависит — машина годится как вторая в сетевых тестах.
- **Сеть.** Лучше всего, когда хост и клиент в одном сегменте сети: мост (bridged) в
  виртуальных машинах, общий bridge на гипервизоре, один коммутатор для железных машин.
- **Общая сеть с NAT** (shared network в Parallels — единственный вариант, когда Mac в сети
  по Wi-Fi). Виртуальные машины видят друг друга, Mac и внешнюю сеть, но машины снаружи к ним
  подключиться не могут. Хост для сетевых тестов ставится снаружи NAT, клиенты — внутри:
  клиент сам начинает обмен, и ответы хоста проходят через NAT.

## 8. Подготовка машин

Для любой машины:

1. Пользователь `olc`; вход по SSH только по ключу.
2. Имя машины в `~/.ssh/config` и запись в `stands.yaml`.
3. Сеть: машина в общем сегменте с остальными стендами.
4. Брандмауэр: входящие SSH (22) и OLC (TCP и UDP `47800`) только из локальной сети.
5. Снапшот после подготовки — «чистая» точка, к которой можно откатиться.

### 8.1. Windows, сборка (`build`)

Пункты 1–3 и 6, а также автозапуск `sshd` делает скрипт
[`tools/stands/setup-windows.ps1`](../tools/stands/setup-windows.ps1): его запускают в
PowerShell от имени администратора (`powershell -ExecutionPolicy Bypass -File .\setup-windows.ps1`),
повторный запуск безопасен. Вручную остаются включение OpenSSH Server, ключ и автовход.

1. Visual Studio 2022 Community с набором «Desktop development with C++». Во вкладке
   Individual Components отметить «C++ MFC for latest build tools (x86 & x64)». На Windows
   ARM дополнительно — «MSVC … C++ x64/x86 build tools»: там средства сборки x64 не ставятся
   по умолчанию.
2. DirectX SDK (June 2010) — по [QUICKSTART.md](QUICKSTART.md).
3. Git для Windows. CMake отдельно не нужен: он входит в Visual Studio.
4. OpenSSH Server: «Параметры → Система → Дополнительные компоненты → OpenSSH Server», служба
   `sshd` — автоматический запуск. Ключ для пользователя-администратора кладётся в
   `C:\ProgramData\ssh\administrators_authorized_keys`, для обычного — в
   `C:\Users\olc\.ssh\authorized_keys`.
5. Автовход пользователя `olc` — чтобы Orbiter можно было запускать на видимом рабочем
   столе (раздел 6).
6. Брандмауэр — правило для TCP и UDP `47800` в частной сети.

Виртуальная машина: 4 ядра и больше, 8 ГБ памяти и больше, 3D-ускорение включено, сеть —
мост. На серверном гипервизоре — драйверы VirtIO (диск, сеть) при установке.

### 8.2. Windows, только запуск (`client`, `host`, `headless-host`)

1. Для картинки — видеокарта с DirectX 9 и актуальный драйвер.
2. Распространяемый пакет Visual C++ 2015–2022 x64 и DirectX End-User Runtime (June 2010):
   D3D9Client нужны библиотеки `d3dx9`. Visual Studio не нужна.
3. OpenSSH Server, пользователь `olc`, автовход, брандмауэр — как в 8.1.

В школах часто ещё Windows 10 — её стоит проверить наравне с Windows 11.

### 8.3. Linux, клиент через Wine (`client`, `host`)

1. Видеокарта с драйвером Vulkan (Mesa для AMD и Intel, проприетарный для NVIDIA).
2. Wine из репозитория WineHQ (stable), `winetricks`; в префикс Wine — `vcrun2022` и
   `d3dx9`; DXVK для перевода DirectX 9 в Vulkan. Точный набор — по
   https://orbiterwiki.org/wiki/Running_Orbiter_under_Wine, уточняется на первом стенде.
3. Графическая сессия с автовходом пользователя `olc` — для запуска Orbiter из SSH.
4. `openssh-server`, ключ, брандмауэр — как для любой машины.

### 8.4. Steam Deck (`client`)

1. Режим рабочего стола, пароль для пользователя `deck`, `sshd` включается через
   `sudo systemctl enable --now sshd`.
2. Orbiter добавляется в Steam как сторонняя игра и запускается через Proton.

### 8.5. Linux или macOS для сетевого ядра (`core-tests`)

1. Компилятор C++, CMake и Git (в Debian и Ubuntu —
   `sudo apt install build-essential cmake git openssh-server`).
2. Сеть — мост, если это виртуальная машина.

Что проверяем: сборку и тесты `olc-core`, обмен пакетами с другой машиной через настоящую
сеть. Orbiter здесь не запускаем.

## 9. Orbiter на стендах

- Orbiter собирается **один раз** — на машине с ролью `build` — по [QUICKSTART.md](QUICKSTART.md).
- Готовый каталог `install` копируется на остальные машины вместе с текстурами планет; путь
  к нему на каждой машине — поле `orbiter` в `stands.yaml`.
- На всех машинах одинаковая сборка Orbiter и одинаковый набор дополнений: это требование
  OLC (решение 17 в [DECISIONS.md](DECISIONS.md)).
- Плагин можно не собирать на стенде: готовая `OrbiterLanCoop.dll` — артефакт сборки в
  GitHub Actions (решение 25).

## 10. Проверка сети: `olc-netcheck`

Утилита из `tools/netcheck/` собирается вместе с ядром (`cmake --build orbiter-lan-coop.out`)
и работает на том же сетевом коде, что и плагин. Orbiter ей не нужен. Если она проходит
между двумя машинами, плагину не помешают ни адреса, ни брандмауэр, ни NAT.

На машине-хосте:

```bash
orbiter-lan-coop.out/tools/netcheck/olc-netcheck server
```

На машине-клиенте (адрес хоста, порт, длительность в секундах, частота PING в секунду):

```bash
orbiter-lan-coop.out/tools/netcheck/olc-netcheck client 192.168.1.10 47800 300 30
```

Клиент проходит рукопожатие `HELLO` → `WELCOME` по TCP, затем шлёт UDP `PING` с частотой
`WORLD_STATE` и печатает потери, задержку туда-обратно (RTT: минимум, среднее, перцентили
50/95/99, максимум), разброс и долю ответов позже 100 и 200 мс. Точность — около 1 мс: цикл
опроса спит по 1 мс.

**Как читать.** Задержка в одну сторону — примерно половина RTT. Буфер сглаживания на
клиенте — 100 мс ([SMOOTHING.md](SMOOTHING.md)): пакет опаздывает, если идёт в одну сторону
дольше. Значит, доля RTT выше 200 мс — это примерно доля кадров, когда клиент будет
экстраполировать вместо интерполяции.

### Замеры

| Дата | Путь | Потери | RTT p50 / p95 / p99 / max, мс | RTT > 200 мс |
|---|---|---|---|---|
| 2026-11-17 | ВМ Parallels (общая сеть, NAT) → Mac по Wi-Fi → проводная ВМ Proxmox; 30 Гц, 300 с | 0 из 9000 | 5,0 / 80,8 / 100,2 / 186,3 | 0% |
| 2026-11-17 | Mac по Wi-Fi → проводная ВМ Proxmox; 30 Гц, 30 с | 0 из 900 | среднее 14,8, max 141,7 | — |

Выводы:

- NAT общей сети Parallels добавляет около 2 мс; задержку раскачивает Wi-Fi.
- Даже по Wi-Fi буфера 100 мс хватило: по оценке (половина RTT) в одну сторону ни один
  пакет не шёл дольше ~95 мс.
  Но запаса мало (p99 RTT — 100 мс), поэтому для сравнения плавности на этапе 1 нужен ещё
  замер по проводу.
- Разброс по Wi-Fi не равномерный, как в модели сглаживания, а с редкими длинными
  всплесками — модель его не проверяла.
