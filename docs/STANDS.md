# Стенды

Как устроена проверка OLC на реальных машинах и как ИИ-агент с ними работает.
Какие стенды для чего — таблица «Стенды» в [PLAN.md](PLAN.md). Здесь — доступ и порядок работы.

> Стенды пока не подключены. Документ описывает согласованную схему; после подключения
> в раздел 5 вносятся реальные имена машин, а гипотезы из раздела 4 — проверяются.

## 1. Схема: один мозг, много рук

- **Мозг** — сессия ИИ-агента на Mac владельца. У неё весь контекст: `docs/`, решения,
  очередь задач. Отдельный Claude на каждом стенде не ставится: это был бы отдельный
  агент со своим контекстом, синхронизацией через git и тем же лимитом аккаунта.
- **Руки** — SSH с Mac на стенды. Сборка, запуск и остановка Orbiter и OLC, сбор логов,
  копирование собранных файлов. Работу на стенде можно поручить субагенту: он запускается
  на Mac и пользуется тем же SSH.
- **Глаза** — только там, где без экрана не обойтись (раздел 3).
- **Запасной вариант** — отдельная сессия Claude на SSH-хосте прямо из приложения Claude.
  Только для долгой автономной работы на Linux-стенде; для Windows-хоста не проверено.

## 2. Доступ

1. На каждой машине — отдельный пользователь `olc`, вход по SSH только по ключу.
2. Отдельный ключ на Mac (`~/.ssh/olc_stands`) и короткие имена машин в `~/.ssh/config`:
   `olc-win-arm`, `olc-win-x86`, `olc-debian` и т. п.
3. Windows: компонент OpenSSH Server, команды — через PowerShell.
4. Доступ только к виртуальным машинам — не к самому Proxmox и не к его API.

## 3. Что делает агент, а что владелец

| Действие | Кто |
|---|---|
| Установка программ (Visual Studio, DirectX SDK, CMake, Wine), системные настройки, брандмауэр | Владелец |
| Снапшоты машин и откат | Владелец |
| Команды docker | Владелец |
| Сборка Orbiter и OLC, запуск и остановка Orbiter, копирование файлов OLC, чтение логов | Агент (решение 20 в [DECISIONS.md](DECISIONS.md)) |

### Как смотреть на картинку

Orbiter — оконное приложение. В Windows программа, запущенная по SSH, работает в
невидимой служебной сессии, а не на рабочем столе. Поэтому:

- **Главное — обходиться без экрана.** Плагин пишет в лог задержку, потери и расхождение
  положений; агент читает лог по SSH. Экран нужен только для итоговой проверки плавности.
- **Parallels:** окно виртуальной машины — это окно на экране Mac; агент смотрит и кликает в
  нём через управление компьютером (computer use).
- **Proxmox:** консоль noVNC во встроенном браузере; в Proxmox входит владелец.
- **Запуск Orbiter на видимом рабочем столе Windows из SSH:** автовход пользователя `olc` и
  запуск через задачу планировщика в интерактивной сессии. Настраивается один раз.
- **Linux:** запуск в графической сессии пользователя (переменная `DISPLAY`).

## 4. Особенности стендов (гипотезы, проверяются на этапе 0)

- **Proxmox без проброса видеокарты.** Нет нормального 3D: D3D9Client в Windows, скорее
  всего, не запустится или будет очень медленным; Wine с DXVK на Linux требует Vulkan.
  Поэтому Proxmox — для хоста без графики («Orbiter Server Console»), сборок и сетевых
  тестов из нескольких машин. Клиенты с картинкой — Parallels, Steam Deck, реальные ПК.
- **Windows 11 ARM в Parallels.** Orbiter x64 работает через встроенную в Windows эмуляцию
  x64: годится для разработки и проверки функций, не для замеров FPS. Эталон — x86.
- **Ubuntu ARM в Parallels.** Wine требует эмуляции x86 — не используем.
- **Сеть.** Хост и клиент должны быть в одном сегменте сети: мост (bridged) в Parallels,
  общий bridge в Proxmox.
