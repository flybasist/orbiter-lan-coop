# Стенды

Как устроена проверка OLC на реальных машинах и как ИИ-агент с ними работает.
Какие стенды для чего — таблица «Стенды» в [PLAN.md](PLAN.md). Здесь — доступ и порядок работы.

> Стенды пока не подключены. Документ описывает согласованную схему; после подключения
> в раздел 9 вносятся реальные имена машин, а гипотезы из раздела 4 — проверяются.

## 1. Схема: один мозг, много рук

- **Мозг** — сессия ИИ-агента на Mac владельца. У неё весь контекст: `docs/`, решения,
  очередь задач. Отдельный Claude на каждом стенде не ставится: это был бы отдельный
  агент со своим контекстом, синхронизацией через git и тем же лимитом аккаунта.
- **Руки** — SSH с Mac на стенды. Сборка, запуск и остановка Orbiter и OLC, сбор логов,
  копирование собранных файлов. Работу на стенде можно поручить субагенту: он запускается
  на Mac и пользуется тем же SSH.
- **Глаза** — только там, где без экрана не обойтись (раздел 3).
- **Запасной вариант** — отдельная сессия Claude на SSH-хосте прямо из приложения Claude.
  Только для долгой автономной работы на Linux-стенде; для Windows-хоста не проверено.

## 2. Доступ

1. На каждой машине — отдельный пользователь `olc`, вход по SSH только по ключу.
2. Отдельный ключ на Mac (`~/.ssh/olc_stands`) и короткие имена машин в `~/.ssh/config`:
   `olc-win-arm`, `olc-win-x86`, `olc-debian` и т. п.
3. Windows: компонент OpenSSH Server, команды — через PowerShell.
4. Доступ только к виртуальным машинам — не к самому Proxmox и не к его API.

## 3. Что делает агент, а что владелец

| Действие | Кто |
|---|---|
| Установка программ (Visual Studio, DirectX SDK, CMake, Wine), системные настройки, брандмауэр | Владелец |
| Снапшоты машин и откат | Владелец |
| Команды docker | Владелец |
| Сборка Orbiter и OLC, запуск и остановка Orbiter, копирование файлов OLC, чтение логов | Агент (решение 20 в [DECISIONS.md](DECISIONS.md)) |

### Как смотреть на картинку

Orbiter — оконное приложение. В Windows программа, запущенная по SSH, работает в
невидимой служебной сессии, а не на рабочем столе. Поэтому:

- **Главное — обходиться без экрана.** Плагин пишет в лог задержку, потери и расхождение
  положений; агент читает лог по SSH. Экран нужен только для итоговой проверки плавности.
- **Parallels:** окно виртуальной машины — это окно на экране Mac; агент смотрит и кликает в
  нём через управление компьютером (computer use).
- **Proxmox:** консоль noVNC во встроенном браузере; в Proxmox входит владелец.
- **Запуск Orbiter на видимом рабочем столе Windows из SSH:** автовход пользователя `olc` и
  запуск через задачу планировщика в интерактивной сессии. Настраивается один раз.
- **Linux:** запуск в графической сессии пользователя (переменная `DISPLAY`).

## 4. Особенности стендов (гипотезы, проверяются на этапе 0)

- **Proxmox без проброса видеокарты.** Нет нормального 3D: D3D9Client в Windows, скорее
  всего, не запустится или будет очень медленным; Wine с DXVK на Linux требует Vulkan.
  Поэтому Proxmox — для хоста без графики («Orbiter Server Console»), сборок и сетевых
  тестов из нескольких машин. Клиенты с картинкой — Parallels, Steam Deck, реальные ПК.
  Если на ноде есть видеокарта для проброса (PCI passthrough) — машина становится полноценным
  клиентом.
- **Windows 11 ARM в Parallels.** Orbiter x64 работает через встроенную в Windows эмуляцию
  x64: годится для разработки и проверки функций, не для замеров FPS. Эталон — x86.
- **Ubuntu ARM в Parallels.** Orbiter там не запустить: Wine требует эмуляции x86. Но
  машина полезна для сетевого ядра OLC — оно не зависит от Orbiter: сборка и тесты под
  Linux и настоящая вторая машина в сети для UDP/TCP-тестов с Mac.
- **Сеть.** Хост и клиент должны быть в одном сегменте сети: мост (bridged) в Parallels,
  общий bridge в Proxmox, один коммутатор для железных машин.

## 5. Базовый дистрибутив Linux

**Debian 13 (trixie).** Почему:

- весь парк владельца на Debian — меньше новых граблей;
- стабильная база, WineHQ выпускает для Debian собственные пакеты;
- для тестов «как у пользователя» дополнительно есть Steam Deck (SteamOS, Proton) — это
  второй путь запуска под Linux, и он закрывает «игровой» сценарий.

Ubuntu 26.04 ARM — только для сетевого ядра (раздел 4). Альт Линукс и Astra Linux имеет
смысл добавить, если ими пользуется космокружок (вопрос кружку): в российских школах они
встречаются часто.

## 6. Общая подготовка любой машины

1. Пользователь `olc`; вход по SSH только по ключу `~/.ssh/olc_stands.pub` с Mac.
2. Имя машины в `~/.ssh/config` на Mac (раздел 9) — по нему работает агент.
3. Сеть: машина в общем сегменте с остальными стендами.
4. Брандмауэр: входящие SSH (22) и OLC (TCP и UDP `47800`) только из локальной сети.
5. Снапшот после подготовки — «чистая» точка, к которой можно откатиться.

## 7. Чек-листы по машинам

### 7.1. Windows 11 Pro ARM в Parallels (основной стенд разработки)

Parallels:
- 4 и больше ядер, 8 ГБ памяти и больше, 3D-ускорение включено;
- сеть — мост (Bridged), чтобы машина была в той же сети, что и остальные стенды.

Windows:
1. Visual Studio 2022 Community с набором «Desktop development with C++». Во вкладке
   Individual Components отметить: «C++ MFC for latest build tools (x86 & x64)» и
   «MSVC … C++ x64/x86 build tools» — на ARM средства сборки x64 не ставятся по умолчанию.
2. DirectX SDK (June 2010) — по [QUICKSTART.md](QUICKSTART.md).
3. Git для Windows. CMake отдельно не нужен: он входит в Visual Studio.
4. OpenSSH Server: «Параметры → Система → Дополнительные компоненты → OpenSSH Server», служба
   `sshd` — автоматический запуск. Ключ для пользователя-администратора кладётся в
   `C:\ProgramData\ssh\administrators_authorized_keys`, для обычного — в
   `C:\Users\olc\.ssh\authorized_keys`.
5. Автовход пользователя `olc` — чтобы Orbiter можно было запускать на видимом рабочем
   столе (раздел 3).
6. Брандмауэр — правило для TCP и UDP `47800` в частной сети.

### 7.2. Ubuntu 26.04 LTS ARM в Parallels (сетевое ядро)

1. `sudo apt install build-essential cmake git openssh-server`.
2. Сеть — мост (Bridged).
3. Пользователь `olc`, ключ в `~/.ssh/authorized_keys`.

Что проверяем: сборку и тесты сетевого ядра под Linux, обмен пакетами Mac ↔ Ubuntu через
настоящую сеть Parallels. Orbiter здесь не запускаем.

### 7.3. Windows 10/11 x86 в Proxmox (хост без графики, сборка, сетевые тесты)

1. Драйверы VirtIO (диск, сеть) при установке.
2. Всё из 7.1, пункты 1–6 (на x86 средства сборки x64 ставятся по умолчанию).
3. Без видеокарты — проверяем запуск Orbiter без графического клиента («Orbiter Server
   Console»). С проброшенной видеокартой — полноценный клиент.
4. Желательно обе версии: Windows 10 22H2 и Windows 11 — в школах часто ещё Windows 10.

### 7.4. Debian 13 x86 в Proxmox (сетевое ядро, Wine без графики)

1. `sudo apt install build-essential cmake git openssh-server`.
2. Без видеокарты — только сетевое ядро и сетевые тесты. С проброшенной видеокартой —
   как железная Linux-машина (7.6).

### 7.5. Железная Windows 10/11 x86 (эталонный клиент)

1. Видеокарта с DirectX 9 и актуальный драйвер.
2. Если машина только запускает Orbiter (не собирает): распространяемый пакет
   Visual C++ 2015–2022 x64 и DirectX End-User Runtime (June 2010) — D3D9Client нужны
   библиотеки `d3dx9`. Visual Studio не нужна.
3. OpenSSH Server, пользователь `olc`, автовход, брандмауэр — как в 7.1.

### 7.6. Железная Linux x86 (клиент через Wine)

1. Debian 13, видеокарта с драйвером Vulkan (Mesa для AMD и Intel, проприетарный для NVIDIA).
2. Wine из репозитория WineHQ (stable), `winetricks`; в префикс Wine — `vcrun2022` и
   `d3dx9`; DXVK для перевода DirectX 9 в Vulkan. Точный набор — по
   https://orbiterwiki.org/wiki/Running_Orbiter_under_Wine, уточняется на первом стенде.
3. Графическая сессия с автовходом пользователя `olc` — для запуска Orbiter из SSH.
4. `openssh-server`, ключ, брандмауэр — как в разделе 6.

### 7.7. Steam Deck (клиент через Proton)

1. Режим рабочего стола, пароль для пользователя `deck`, `sshd` включается через
   `sudo systemctl enable --now sshd`.
2. Orbiter добавляется в Steam как сторонняя игра и запускается через Proton.

## 8. Orbiter на стендах

- Orbiter собирается **один раз** — на машине из 7.1 или 7.3 — по [QUICKSTART.md](QUICKSTART.md).
- Готовый каталог `install` копируется на остальные машины вместе с текстурами планет.
- На всех машинах одинаковая сборка Orbiter и одинаковый набор дополнений: это требование
  OLC (решение 17 в [DECISIONS.md](DECISIONS.md)).
